排行榜（Rank / 排行榜）机制详解

基于 c_server 代码库逆向梳理 · 覆盖实时榜、离线榜、内存榜三套实现

核心模块：majorserver/module/ranklist · serverfw/rank/redisrank · datacenter/offline_rank

Redis ZSET MySQL 离线榜 Kafka binlog 同分时间排序 分布式重建锁 LRU 缓存

0总览

这套排行榜系统不是单一实现，而是按「数据规模 / 实时性 / 是否跨进程」划分的三套并存的机制。 业务方通过 ranklist 模块的接口拿到对应的榜单句柄，而底层落地到 Redis、MySQL 或纯内存。

① Redis 实时榜 redisrank

基于 Redis ZSET，多进程共享、强实时。用于活动榜、竞技场等需要即时写入/查询排名的场景。支持「同分按时间排序」。

② 离线榜 offline_rank

由 DataCenter 消费 Kafka binlog 自动维护，落地 MySQL 分表。用于战力榜、击杀榜等「玩家数据天然存在、不想业务侧主动写榜」的常驻大榜。

③ 内存简易榜 util.TRank

单进程内 slice + 读写锁 + 插入排序。用于临时、单服、量小的榜（如某活动内的伤害进度榜）。

一句话区分：需要业务主动 AddScore/SetScore 且跨进程 → Redis 实时榜； 数据本来就写在玩家/军团表里、只想"自动成榜" → 离线榜； 只在一个进程内、临时用一下 → 内存榜。

2Redis 实时榜（redisrank.TRank）

serverfw/rank/redisrank/rank.go

目标注释写得很直接："支持多个进程同时访问的排行榜"。每个榜对应一个 Redis ZSET， 分数越大排名越靠前（ZRevRange）。

2.1 ZSET 存储模型

榜单对象 TItem 三要素：

type TItem struct {
    Id          string   // 元素唯一id（uid / gid 字符串化）
    Score       float64  // 得分，越大排名越靠前
    TimeStampMs int64    // 得分对应时间戳，仅开启时间排序时有效
}

读写直接映射到 Redis 命令：

业务操作底层 Redis 命令
写入 / 更新 SetItemZADD（无时间排序）或 Lua 脚本（有时间排序）
取 TopN GetList(offset,limit)ZREVRANGE ... WITHSCORES
按分数区间 GetListByScoreRangeZREVRANGEBYSCORE / ZRANGEBYSCORE
查排名 GetRankByIdZREVRANK（+1，因 Redis 从 0 计）
查分数 GetItemByIdZSCORE
批量查 GetItemsByIdsPipeline 批量 ZSCORE
删除 DelByIdZREM
长度 GetCurrLenZCARD

2.2 重建（Rebuild）、过期、裁剪

① 懒重建 + 分布式锁

榜首次访问或收到重建标志时触发 doRebuild()。多进程并发由 Redis 锁 TryLock(rebuild_lock, 30s) 串行化，重建在临时 ZSET 上完成后 RENAME 原子切换，避免读到半成品。

// 整体重建流程（节选）
this.delKey(getRebuildZSetKey(name))           // 删临时key
for i := 0; i < len(allItem); i += ZADD_BATCH_COUNT {  // 每批200条
    this.redisCli.ZAdd(getRebuildZSetKey(name), zArr...)
}
this.renameKey(getRebuildZSetKey(name), getZSetKey(name))  // 原子切换

② 滚动榜：从上期榜拷贝

周期性榜（如竞技场每日榜）首次重建时，若配置了 lastRankName，会用 copyRank.lua 直接从上期 ZSET 拷贝作为初始排名——"今天的榜以昨天为基础"。

③ 过期处理

后台 routineRun() 每分钟检查：超过 GetExpirtTime() 的榜不直接删，而是 RENAME 到 backup key 并设 30 天 TTL（可回溯）。注册时过期时间 = endTime + DefaultExpireHours(14天)。

④ 长度裁剪

有上限的榜，仅当元素数 > maxLen × 1.2（CHECK_LEN_COEF）才触发 ZRemRangeByRank 删掉低分尾部——避免每次写入都裁剪，降低开销。

3同分排序（Tie-break）——本系统的精华

Redis ZSET 同分时按 member 字典序排，这不符合游戏需求（通常希望"先达到该分数的玩家排前面"）。 本系统提供了两套互补方案。

3.1 方案 A：分数-时间位编码（在 TRankListSingle 层）

majorserver/module/ranklist/ranklistimpl/ranklist_single_obj.go

把"真实分数"和"时间偏移"打包进同一个 64 位浮点分数，让 ZSET 一次比较即完成"先比分、再比时间"。 定义了两种位宽布局：

活动榜布局 LittleTimeInScore（分数大、时间窗口小）

Score · 高 32 位
积分上限 ≈ 42.9 亿
Time · 低 21 位
时间窗 ≈ 24.27 天

常驻榜布局 BigTimeInScore（分数小、时间窗口大）

Score · 高 21 位
积分上限 ≈ 209 万
Time · 低 32 位
时间窗到 2050 年

编码核心 getValFromScoreTime：把分数左移到高位，再加上"时间偏移"。 关键技巧是存 timeOffset = endTime − updateTime（剩余时间）， 这样更新越早 → 剩余越大 → 低位越大 → 同分时排名越靠前。

timeOffset := endTime - updateTime        // 越早更新，offset 越大
rScore := aScore << TimeBitLength          // 分数占高位
rScore += uint64(timeOffset)               // 时间占低位
// 读取时再 getScoreTimeFromVal 用掩码 & 位移还原真实分数与时间
取舍：位编码零额外存储、单次 ZADD 即可，但积分/时间范围受位宽限制， 超限会被截断（代码里有 Warning + clamp）。活动榜因此被限定"时长 ≤ 24.27 天、积分 ≤ 42.9 亿"。

3.2 方案 B：TimeSortLevel + 独立 timeHash + Lua（在框架层）

当不想牺牲分数精度时，框架层提供另一种：分数照常存，时间戳单独存一个 Hash， 并把时间编进 ZSET 的 member 里参与字典序。三档：

TimeSortLevel含义
TimeSortNone(0)不开启，同分按默认
TimeSortReverseWithScore(1)同分时，时间小的靠前（member 存 maxTs − ts）
TimeSortSameWithScore(2)同分时，时间大的靠前（member 存 ts）

因为要同时改 ZSET 与 timeHash，写/查/删都用 Lua 脚本保证原子性 （updateById.lua / getRankById.lua / delById.lua / clear.lua）。例如更新：

-- updateById.lua（节选）：先按旧时间戳删旧 member，再写新 member
local oldTs = redis.call('HGET', timeHashKey, id)
if oldTs then
    local oldZSetId = tostring(maxTs - tonumber(oldTs)) .. sep .. id
    redis.call('ZREM', rankZSetKey, oldZSetId)
end
redis.call('HSET', timeHashKey, id, newTs)             -- 更新时间戳
local newZSetId = tostring(maxTs - tonumber(newTs)) .. sep .. id
return redis.call('ZADD', rankZSetKey, tonumber(newScore), newZSetId)
两种方案对应不同诉求：方案 A省存储但限范围、适合活动榜；方案 B不限分数范围但多一份 timeHash + Lua 开销、适合常驻精确榜。

4离线榜（offline_rank）——玩家/军团常驻大榜

datacenter/offline_rank/rank_manager.go · builtin_rank.go

这是日常"战力榜 / 击杀榜 / 主城等级榜 / 军团榜"等的实现。最大特点： 业务侧完全不主动写榜，而是 DataCenter 监听数据库变更自动成榜。

处理逻辑（UpdateByKafka）：

  1. 解析消息所属表，识别是玩家表(uid)还是军团表(gid)；
  2. 玩家：反查其所属 gid 与 botType——机器人玩家直接不入榜；
  3. 遍历变更字段，用 {Column, TableName, DbType} 组成 srcKey 找关联的榜单 schema；无关联则跳过；
  4. 命中则把该字段新值 UPSERT 到对应的榜单分表行。
退团回调 OnUserQuitGuild 会自动把该玩家从所有"军团范围"的榜单表删除，保证军团内榜的正确性。

4.2 榜单定义 TRankSchema

每个离线榜由一份 schema 描述，配置驱动、可同步到 DB：

字段说明
ItemType榜元素类型：User / Guild
RangeType范围：单服 / 单军团 / 多军团（决定分表 key）
PeriodType周期：None / Day / Week（决定是否带 periodKey、是否定期清理）
SortFields多字段排序，依次比较。如战力榜：先 cur_fight_force DESC，再 cur_fight_force_change_time ASC（同战力先达到者靠前）
NeedUpdateTimestamp是否记录更新时间戳，用于"只统计满足时间条件的元素"过滤
MaxNum / ExpireTimeUnix榜容量上限 / 过期时间（0 表示不限 / 永久）

分表策略

榜单表名 = 前缀 + _rankKey [+ _periodKey]。例如军团每周贡献榜： t_rank_list_user_weekly_donate_in_guild_{gid}_{20250707}。 rankKey 通常是 sid 或 gid，periodKey 是日期。周期表由 cron purge_expired_rank_list（每小时）自动 drop 过期表。

5对外 RPC 与缓存层

ranklistimpl/ranklist_rpc.go · ranklist_logic.go · ranklist_local_cache.go

5.1 客户端入口

RPC作用
RpcGetRankListTotalInfo排行榜总览：每个榜取 Top1 拼成一屏概览
RpcGetRankListInfo单个榜详情：TopN + 自己的排名/分数
...ByInner 版本：跨服查询时，本服 RPC 调用目标服的 Inner 接口

权限由 GameCondition 控制；"自己"的那条若不在 TopN 内，则现场用 getSelfRankScoreByRankListType 实时取值补构造一条。

5.2 进程内 LRU 缓存

离线榜每次查 DataCenter 成本较高，于是 ranklist_local_cache.go 加了一层 gcache LRU：

  • 容量 1000，过期 1 小时；key = {rankListType, rankKey, periodKey}；
  • miss 时由 rankListTopMemberInfoLoader 拉离线榜 Top（战力榜 200、军团榜 50、其余 100）并填充玩家/军团展示信息；
  • 提供 HTTP 命令 clearRankCache 与 removeRankCache 手动失效；
  • 后台每 10s 打印命中率统计。
因此玩家看到的离线榜有最长 1 小时延迟（缓存窗口），这是用一致性换性能的典型取舍。

6事件驱动的榜数据刷新

ranklistimpl/ranklist_update_logic.go

离线榜靠 binlog，但有些"聚合值"（如军团总战力 = 成员战力之和）并不直接存在某个字段里， 需要业务在相关事件发生时先把聚合值写回 DB 字段，binlog 再驱动入榜。

// 事件 → 需要刷新的榜类型
var RankListEvent = map[int32][]pb.RankListType{
    event.EventHeroUpgrade:   {pb.RankListType_GuildPower},   // 英雄升级→军团战力
    event.EventGuildJoin:     {pb.RankListType_GuildPower, pb.RankListType_GuildKill},
    event.EventGuildQuit:     {pb.RankListType_GuildPower, pb.RankListType_GuildKill},
    // ...建筑、科研、军团增减员等
}

例如玩家退团 (EventGuildQuit)：异步在事务里把该玩家的战力/击杀从军团聚合值中扣减， 写入 t_guild_stat，随后 binlog 自动更新军团榜。整个过程加 LockGuildData 防并发。

7本地内存简易榜（util.TRank）

majorserver/util/rank_simple.go

最轻量的实现：一个带 sync.RWMutex 的 []*TRankItem 切片， 每次 ProgressAdd/Set 后做局部递归冒泡把变动项移到正确位置（接近 O(n) 但单次移动很短）。

  • 同分 tie-break：compareThan 内置——升序榜同分时 ChangeTime 小的靠前；
  • removeZero 选项可在进度归零时自动出榜；
  • 仅单进程有效、重启即失，适合活动期间的临时榜。

8Redis Key 命名一览

所有 key 带 {__ranker} hash-tag，保证 Redis Cluster 下同一榜的多个 key 落同一 slot。

用途Key 格式
榜单 ZSET{__ranker}_zset_<name>
时间 Hash（时间排序用）{__ranker}_time_hash_<name>
重建临时..._zset_<name>_for_rebuild
过期备份..._zset_<name>_for_backup（TTL 30天）
重建标志 / 时间 / 锁{__ranker}_rebuild_flag/time/lock_<name>

其中 <name> = 业务名 + id + serverId（见 GetRankName）。

9设计要点总结

① 多实现按场景分流

实时榜(Redis)/离线榜(MySQL+Kafka)/内存榜三套并存，业务按"实时性·规模·跨进程"选型，统一接口收口。

② 同分排序双方案

位编码（省存储、限范围、活动榜）与 timeHash+Lua（不限范围、精确、常驻榜）互补。

③ 离线榜零侵入成榜

消费 binlog 自动维护，业务不写榜；聚合类指标用事件回写 DB 字段间接驱动。

④ 一致性换性能

LRU 缓存 1h、长度超 1.2 倍才裁剪、批量 ZADD/Pipeline，均为吞吐优化。

⑤ 分布式安全

重建用 Redis 锁 + 临时 key RENAME 原子切换；多 key 操作用 Lua 原子化。

⑥ 数据治理

机器人不入榜、退团清榜、周期表 cron 清理、过期榜备份 30 天可回溯。

典型调用链回顾：
玩家升级英雄 → 战力字段变更写 DB → Kafka binlog → DataCenter 入 user_ff 榜（MySQL）→ 客户端拉榜命中 LRU 缓存（≤1h）→ 缓存 miss 时回源 DataCenter Top200 → 拼装玩家展示信息返回。
