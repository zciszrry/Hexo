GC (Garbage Collection，垃圾回收)是编程语言中提供的自动的内存管理机制，自动释放不需要的对象，让出存储器资源，无需程序员手动执行。

## 标记-清除算法（Go V1.5以前）

操作：暂停程序业务逻辑，分类出可达和不可达的对象，标记可达对象，标记完了之后，然后开始清除未标记的对象。

Mark and Sweep算法在执行的时候，需要程序暂停，即 STW（Stop The World）。STW的过程中，CPU不执行用户代码，全部用于垃圾回收，这个过程的影响很大。

## 三色并发标记法+插入屏障（Go V1.5)

三色标记法将对象分为三类，并用不同的颜色相称：

- 白色对象（可能死亡）：未被回收器访问到的对象。在回收开始阶段，所有对象均为白色，当回收结束后，白色对象均不可达。
- 灰色对象（波面）：已被回收器访问到的对象，但回收器需要对其中的一个或多个指针进行扫描，因为他们可能还指向白色对象。
- 黑色对象（确定存活）：已被回收器访问到的对象，其中所有字段都已被扫描，黑色对象中任何一个指针都不可能直接指向白色对象。

标记过程如下：

（1）起初所有的对象都是白色的；

（2）从根对象出发扫描所有可达对象，标记为灰色，放入待处理队列；

（3）从待处理队列中取出灰色对象，将其引用的对象标记为灰色并放入待处理队列中，自身标记为黑色；

（4）重复步骤（3），直到待处理队列为空，此时白色对象即为不可达的“垃圾”，回收白色对象；

**并发（Concurrent）**。GC的标记阶段与用户程序**同时运行**。

但无屏障机制的三色并发标记法会导致可达对象的误清除，需要从以下屏障策略二选一：

- **插入屏障（强三色不变式）**：确保**黑色对象永远不能指向白色对象**。只要黑色对象指向了白色，就立刻把白色变灰。
- **删除屏障（弱三色不变式）**：允许黑色对象指向白色，但确保所有**灰色对象到白色对象的路径**不会被破坏。

Go V1.5实际采用的是插入屏障。又因为黑色对象的内存槽有两种位置, `栈`和`堆`. 栈空间的特点是容量小,但是要求相应速度快,因为函数调用弹出频繁使用, 所以“插入屏障”机制,在**栈空间的对象操作中不使用**. 而仅仅使用在堆空间对象的操作中.

所以要对栈重新进行三色标记扫描, 但这次为了对象不丢失, 要对本次标记扫描启动STW暂停. 直到栈空间的三色标记结束.

## 混合写屏障（Go V1.8)

`具体操作`:

1、GC开始将栈上的对象全部扫描并标记为黑色(之后不再进行第二次重复扫描，无需STW)，

2、GC期间，任何在栈上创建的新对象，均为黑色。

3、被删除的对象标记为灰色。

4、被添加的对象标记为灰色。

`满足`: 变形的**弱三色不变式**.

混合写屏障满足`弱三色不变式`，结合了删除写屏障和插入写屏障的优点，只需要在开始时并发扫描各个goroutine的栈，使其变黑并一直保持，这个过程不需要STW，而标记结束后，因为栈在扫描后始终是黑色的，也无需再进行re-scan操作了，减少了STW的时间。

## Green Tea优化（Go V1.26)

问题：随机跳跃的图泛洪

图泛洪的工作模式决定了它在内存访问上的随机性：

```css
扫描对象 A → 发现指针 → 跳到内存某处的对象 B → 发现指针 → 跳到另一处的对象 C → …
```

两个相互引用的对象，在内存里未必相邻，往往差了几 KB 甚至几 MB。每次跳转，CPU 都要等待新地址的数据从主存加载进来。现代 CPU 的 L1 缓存命中只需 4 个时钟周期，而主存访问可能需要几百个周期——差了将近 100 倍。

更糟的是，每次扫描的工作量很小，而且高度依赖上一次的结果（得到指针之后才知道下一步去哪），CPU 的乱序执行和预取机制完全无法发挥作用。一位 Go 团队的工程师把这种情况直接称为"**微架构灾难**"。

### Green Tea 的核心思想

Go 团队给出的解法只有一句话：

**以页（page）为单位追踪和扫描，而不是以对象为单位。**

Go 运行时中，页（page）是 8 KiB 的连续对齐内存块，同一页内的对象大小相同。这个特性，是 Green Tea 一切优化的基础。

### 具体改了什么

原始 mark-sweep 的工作列表里放的是**对象**，Green Tea 的工作列表里放的是**页**。

同时，每个对象的元数据从 1 bit 变成 2 bit：

- **seen bit**：是否发现过指向该对象的指针
- **scanned bit**：是否已经扫描过该对象的指针

扫描流程变成：

1. 从工作列表里取出一个**页**；
2. 对比该页所有对象的 seen bit 和 scanned bit，找出"已发现但未扫描"的对象；
3. 按内存顺序依次扫描这些对象（它们都在同一页内，物理上相邻）；
4. 扫描中发现新指针时，把目标对象所在的**页**加入工作列表（如果不在的话），并设置目标对象的 seen bit。

关键变化在于：**同一页内的多个对象被集中在一次工作流中处理**，而不是每发现一个对象就立刻去追它的指针。工作列表使用先进先出（队列）而非先进后出（栈），目的是让页在队列中等待时，能尽量积累更多待扫描对象，从而在一次处理中扫更多内容。

Green Tea 的核心假设是"同一页内可以积累到足够多的待扫描对象"。如果程序的对象图非常稀疏，每次只能在同一页内扫到 1~2 个对象，那么 Green Tea 积累等待的开销反而会超过收益。Go 团队对这种情况做了特殊处理（单对象页直接走简化路径），但尚未完全消除这类场景下的回退。





# Go 垃圾回收（GC）机制演进详解

## 1. 垃圾回收概述

GC（Garbage Collection，垃圾回收）是现代编程语言提供的一种**自动内存管理机制**。它能够在程序运行时自动识别并回收不再被使用的对象，释放其所占用的内存资源，从而避免手动内存管理带来的野指针、内存泄漏、重复释放等一系列问题，大幅降低开发者的心智负担和程序崩溃风险。

---

## 2. 标记-清除算法（Go V1.5 以前）

### 2.1 算法流程

标记-清除（Mark-Sweep）算法是 Go 早期版本采用的 GC 核心算法，其基本操作流程如下：

1. **暂停程序**：GC 开始时，暂停所有用户程序（即业务逻辑）的执行，进入 STW（Stop The World）状态。
2. **标记阶段**：从根对象（全局变量、栈变量、寄存器等）出发，遍历所有可达对象，并将其标记为“存活”。
3. **清除阶段**：遍历整个堆内存，回收所有未被标记的对象，将其内存归还给空闲链表或内存池。

### 2.2 STW 的影响

在标记-清除算法执行期间，CPU 完全用于垃圾回收工作，不执行任何用户代码。对于延迟敏感型应用（如 Web 服务、实时系统），这种长时间的全局停顿会带来显著的性能抖动，甚至影响服务的可用性和用户体验。

### 2.3 版本演进对比

**V1.3 以前**：GC 全程 STW，且标记和清除阶段均需暂停用户程序，停顿时间与堆内存大小成正比。

**V1.3 优化**：将清除阶段改为并发执行，但标记阶段仍需 STW，停顿时间依然较长。

> 示意图：
> - V1.3 以前：`[STW 标记] → [STW 清除]`
> - V1.3 优化：`[STW 标记] → [并发清除]`

---

## 3. 三色并发标记法 + 插入屏障（Go V1.5）

### 3.1 三色标记法概述

三色标记法将对象分为三类，并用不同颜色标识其状态：

| 颜色     | 含义           | 说明                                                         |
| -------- | -------------- | ------------------------------------------------------------ |
| **白色** | 可能死亡       | 未被回收器访问到的对象。GC 开始时所有对象均为白色，GC 结束后白色对象被判定为不可达并回收 |
| **灰色** | 波面（待处理） | 已被回收器访问到，但其引用的子对象尚未全部扫描完成，需要进一步处理 |
| **黑色** | 确定存活       | 已被回收器访问且所有引用的子对象均已扫描完毕。黑色对象不可能直接指向白色对象 |

### 3.2 三色标记流程

标记过程分为以下四个步骤：

1. **初始化**：所有对象初始均为白色。
2. **根扫描**：从根对象出发，扫描所有可达对象，将其标记为灰色并放入待处理队列。
3. **队列处理**：从待处理队列中取出灰色对象，将其引用的所有对象标记为灰色并入队，自身标记为黑色。
4. **循环结束**：重复步骤 3 直至待处理队列为空。此时白色对象即为不可达的“垃圾”，将被回收。

### 3.3 并发标记的问题与屏障机制

Go V1.5 引入了**并发标记**，即 GC 的标记阶段可以与用户程序同时运行。但无屏障机制的三色并发标记可能导致**可达对象被误清除**（即白色对象被黑色对象引用，但黑色对象已标记完成不再扫描）。

为解决此问题，必须引入以下两种写屏障策略之一：

- **插入屏障（强三色不变式）**：确保**黑色对象永远不能指向白色对象**。一旦黑色对象新增指向白色对象的指针，立即将白色对象标记为灰色，防止其被误清除。
  
- **删除屏障（弱三色不变式）**：允许黑色对象指向白色对象，但必须保证**所有灰色对象到白色对象的路径不会被破坏**。当灰色对象删除对白色对象的引用时，需要将该白色对象标记为灰色。

### 3.4 Go V1.5 的实际实现

Go V1.5 实际采用**插入屏障**。但由于栈空间具有以下特点：
- 容量小，但访问频繁
- 函数调用时栈帧频繁出入，要求极高的响应速度

因此，**插入屏障仅在堆空间生效，栈空间不使用插入屏障**。这导致需要对栈单独进行一次三色标记扫描，且此次扫描必须**启动 STW** 以保证对象不丢失。STW 直到栈空间的三色标记结束才释放。

---

## 4. 混合写屏障（Go V1.8）

### 4.1 具体操作规则

Go V1.8 引入了混合写屏障，其具体操作规则如下：

| 步骤 | 操作内容                                                     |
| ---- | ------------------------------------------------------------ |
| 1    | GC 开始时，将**所有栈上的对象**全部扫描并标记为黑色（此后不再二次重复扫描，**无需 STW**） |
| 2    | GC 期间，**任何在栈上新创建的对象**均直接标记为黑色          |
| 3    | 被删除引用的对象，标记为灰色                                 |
| 4    | 被新增引用的对象，标记为灰色                                 |

### 4.2 不变式满足

混合写屏障满足**变形的弱三色不变式**，它结合了删除写屏障和插入写屏障的优点：
- 仅需在 GC 开始时并发扫描各个 goroutine 的栈并使其变黑
- 扫描过程**无需 STW**
- 标记结束后，因栈始终保持黑色，**无需 re-scan 操作**

最终效果是**大幅减少了 STW 时间**，将 Go GC 的暂停时间从数十毫秒降低到毫秒级甚至微秒级。

## 5. Green Tea 优化（Go V1.26）

### 5.1 问题背景：随机跳跃的图泛洪

随着堆内存规模的持续增长，三色标记法的图泛洪（graph flooding）工作模式暴露出严重的性能瓶颈：

- 扫描对象 A → 发现指针 → 跳转到内存某处的对象 B → 发现指针 → 跳转到另一处的对象 C → …
- 两个相互引用的对象在内存中往往并不相邻，可能相差数 KB 甚至数 MB
- 每次跳转，CPU 都需要等待新地址的数据从主存加载

**微架构灾难**：现代 CPU 的 L1 缓存命中仅需约 4 个时钟周期，而主存访问可能需要数百个周期——性能差异接近 100 倍。更严重的是，每次扫描的工作量很小且高度依赖上一次的结果（得到指针后才知道下一步去哪），CPU 的乱序执行和预取机制几乎完全失效。Go 团队工程师将此情况称为 **“微架构灾难”**。

### 5.2 Green Tea 的核心思想

Go 团队的解决策略非常简单直接：

> **以页（page）为单位追踪和扫描，而不是以对象为单位。**

Go 运行时中，页是 8 KiB 的连续对齐内存块，且**同一页内的对象大小相同**。这一特性是 Green Tea 一切优化的基础。

### 5.3 具体改动

| 改动项       | 原始方案          | Green Tea 方案                      |
| ------------ | ----------------- | ----------------------------------- |
| 工作列表单位 | 对象              | **页**                              |
| 对象元数据   | 1 bit（存活标记） | **2 bit**（seen bit + scanned bit） |

**2 bit 含义**：
- **seen bit**：是否发现过指向该对象的指针
- **scanned bit**：是否已经扫描过该对象的指针

### 5.4 扫描流程

1. 从工作列表中取出一个**页**。
2. 对比该页所有对象的 seen bit 和 scanned bit，找出“已发现但未扫描”的对象。
3. **按内存顺序**依次扫描这些对象（因它们在同一页内，物理上相邻，CPU 缓存友好）。
4. 扫描中发现新指针时，将目标对象所在的**页**加入工作列表（若尚未存在），并设置目标对象的 seen bit。

### 5.5 关键优化点

- **集中处理**：同一页内的多个对象被集中在一次工作流中处理，而不是每发现一个对象就立即追踪其指针。
- **FIFO 队列**：工作列表采用先进先出（队列）而非先进后出（栈），让页在队列中等待时能积累更多待扫描对象，从而在一次处理中扫描更多内容。
- **缓存友好**：按内存顺序扫描，大幅提升 CPU 缓存命中率，减少主存访问。

### 5.6 适用场景与边界情况

Green Tea 的核心假设是：**同一页内可以积累到足够多的待扫描对象**。

- **适用场景**：对象密度较高、指针关系密集的程序，性能提升显著。
- **边界情况**：若对象图非常稀疏，每次只能在同一页内扫描 1~2 个对象，Green Tea 的积累等待开销反而可能超过收益。

Go 团队对此做了特殊处理：**单对象页直接走简化路径**，但在极端稀疏场景下仍存在一定的性能回退，尚未完全消除。

## 6. 总结对比

| 版本      | GC 算法                       | STW 时间               | 核心特点                                 |
| --------- | ----------------------------- | ---------------------- | ---------------------------------------- |
| V1.3 以前 | 标记-清除（全 STW）           | 较长（与堆大小成正比） | 全程暂停用户程序                         |
| V1.3      | 标记 STW + 清除并发           | 中等                   | 清除阶段并发，减少部分停顿               |
| V1.5      | 三色并发标记 + 插入屏障（堆） | 较短                   | 引入并发标记，但栈需 re-scan             |
| V1.8      | 混合写屏障                    | 极短（毫秒级）         | 栈全黑 + 无需 re-scan，STW 大幅降低      |
| V1.26     | Green Tea（以页为单位扫描）   | 微秒级                 | 缓存友好，减少主存访问，缓解“微架构灾难” |

从 Go V1.5 到 V1.26，Go GC 经历了从“秒级停顿”到“毫秒级停顿”再到“微秒级停顿”的持续演进，在吞吐量和延迟之间不断寻求更优的平衡，为大规模高并发服务提供了坚实的内存管理基础设施。
